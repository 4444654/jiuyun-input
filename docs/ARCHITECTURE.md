# 架构与数据流

玖云采用「同一份词库、同一组双拼规则、不同系统接入」的结构。Web、Java、Swift 引擎是独立移植，不是将网页套壳成系统输入法。

## 数据源

packages/lexicon/starter.json 保存人工编写的 452 条基础词条，每项包含 text、带空格的无声调 pinyin 和 weight。扩充请只引入许可清楚的数据。packages/core/shuangpin.mjs 定义 8 套键位和零声母规则。packages/schemes/builtin.json 及移动端 JSON 均为生成文件。

npm run generate 生成移动端词库、方案表、桌面原始全拼词库，以及 8 组双拼词典与方案。--check 用于持续集成检测源文件与生成结果是否一致。--scheme 可以额外生成一组个人桌面方案。

## Web 输入流程

键盘事件 → 组字编码 → 按当前方案建立的索引 → 精确/前缀候选和基础词典分句 → 排序去重 → 候选选词 → 编辑器。

双拼编码每个音节产生两键。全拼模式另支持首字母简拼。简化分句使用动态规划，偏好较长词条；它没有上下文语言模型。字词未在词库中时，无法靠双拼规则凭空补出汉字。保留 Enter 提交原始编码。

排序优先级：精确匹配、已知词典组合、全拼首字母匹配、前缀匹配。词频学习只在各匹配层内提高候选位置，不上传使用数据。各方案之间可能出现同码词频互相影响；后续可进一步按方案隔离学习数据。

编辑正文只存在当前页内存，刷新丢失；设置、个人词条、自定义方案、已选词频存在 localStorage。Service Worker 只缓存同源应用资源。没有后端接口、账号、分析事件或第三方资源。

## 原生端

Android 用 InputMethodService / InputConnection 设置组字和提交候选，SharedPreferences 保存当前方案及本地词频。iOS 用 UIInputViewController / textDocumentProxy 提交候选，UserDefaults 保存扩展私有方案及词频。两端读取生成的相同词库和方案表。当前还没有原生候选性能基准和跨端引擎对照运行结果。

Windows 主方案直接使用 TSF，系统接入改造自微软 MIT 开源 SampleIME；独立设置程序控制词典方案，安装器注册 32/64 位服务。Rime 仅作为可选兼容适配。macOS / Linux 当前仍通过可选 Rime 适配接入，独立原生实现尚未完成。双拼使用独立生成的码表，避免依赖外部大词库；全拼使用 script_translator。桌面候选排版由小狼毫、鼠须管或 Linux 宿主提供。

## 验证范围

31 项自动测试覆盖全拼精确/简拼/前缀候选、基础分句、个性词频、自定义词条，以及全部 8 套双拼的已知编码、零声母、分号、整词与组合、自定义映射校验。另有语法和生成文件同步检查。

本地没有 Windows C++ SDK、Android SDK/JDK 或 macOS/Xcode。原生包交给 GitHub Actions 实际编译；远程构建是否成功必须读取运行结果。创建流程文件不代表编译通过。网页选词、分号键、主题和自定义键位预览已在 ego 中实际验证。
